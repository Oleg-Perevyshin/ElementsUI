# 📦 Где публиковать библиотеку и витрину

Справка для ИИ и разработчика: откуда приложения стека берут `poe-svelte-ui-lib`, где живёт витрина и какие есть варианты перенести всё в свою инфраструктуру (Forgejo, Harbor, ArgoCD). Здесь собраны факты о кластере, варианты с плюсами и минусами и рекомендация. Решение принимает владелец. Пока он не скажет иначе, действует то, что описано в разделе «Как сейчас».

## ✨ Коротко

- **Как сейчас.** Библиотека публикуется в npmjs, витрина живёт на GitHub Pages, исходники на GitHub. Так и оставлять, пока нет причины менять.
- **Свой npm - только Forgejo.** Harbor хранит образы Docker и OCI-артефакты, npm он не умеет.
- **У Forgejo нет своих Pages.** Витрину у себя разворачивают так же, как Web Studio: образ nginx в Harbor, ArgoCD, домен через Traefik.
- **Если переезжать, то целиком.** Исходники на Forgejo, CI на своём runner, пакет в реестре Forgejo со scope, витрина образом в кластере, GitHub - зеркало.

## 🧭 Как сейчас

| Что                       | Где                                                               | Как обновляется                                                                                                                                             |
| ------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Исходники ElementsUI      | GitHub `Oleg-Perevyshin/ElementsUI`                               | Зеркало на Forgejo отстаёт и не используется                                                                                                                |
| Пакет `poe-svelte-ui-lib` | npmjs, публичный, закрытая лицензия (`SEE LICENSE IN LICENSE.md`) | Коммит с `[publish]`, job `publish` в `.github/workflows/npm_publish.yaml`, публикация по OIDC                                                              |
| Облако DevCloud           | git.xpoe.pro, образ в Harbor                                      | Job `update-devcloud` того же workflow ставит новую версию в DevCloud и коммитит `X.Y [deploy] Обновление ElementsUI до X.Y.Z`, дальше CI облака на Forgejo |
| Витрина                   | GitHub Pages, путь `/ElementsUI`                                  | Коммит с `[deploy]`, `.github/workflows/ghpages_deploy.yaml`, сборка в `docs/`                                                                              |
| DevTerminal, WebApp ESP   | Локально у разработчика                                           | `npm install poe-svelte-ui-lib@^X.Y.Z` вручную в том же выпуске                                                                                             |

**Что уже случалось.** Метаданные новой версии в npm (`npm view`) появляются раньше, чем реестр начинает отдавать сам архив `.tgz`. Из-за этого обновление облака до 3.3.1 упало с `404`. Теперь `update-devcloud` ждёт сам архив (`npm pack --dry-run`) и повторяет установку до 5 раз.

## 🧩 Варианты для пакета

| Вариант                      | Суть                                                                             | Плюсы                                                                                                  | Минусы                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **A. Только npmjs** (сейчас) | Как есть                                                                         | Ничего не менять. Пакет публичный, ставится откуда угодно без токена. Витрина и `provenance` на GitHub | Зависимость от GitHub и npmjs. Задержка раздачи новой версии, уже закрыта ожиданием в CI                 |
| **B. npmjs + Forgejo**       | Тот же выпуск публикуется в оба реестра. Приложения стека берут пакет из Forgejo | Внутренние сборки не ждут npmjs. Публичный пакет остаётся                                              | Два реестра, второе имя пакета со scope, токены в CI                                                     |
| **C. Только Forgejo**        | Исходники, CI и пакет у себя. GitHub - зеркало или ничего                        | Всё в своей сети, пакет можно закрыть, версия доступна сразу после публикации                          | Нужен переезд CI. Ставить пакет можно только с токеном, если он закрыт. Витрину разворачивать в кластере |
| **D. Verdaccio в кластере**  | Отдельный npm-сервер, проксирует npmjs                                           | Один адрес реестра для всех пакетов, кэш npmjs                                                         | Ещё один сервис и том Longhorn. Forgejo уже умеет то же самое для своих пакетов                          |

**Рекомендация.**

- Пока пакет публичный и задержек нет, оставаться на **A**.
- Если нужна независимость от GitHub или закрытая библиотека - сразу **C**, без промежуточного B. Двойная публикация удваивает места, где может сломаться выпуск, а пользы даёт мало.
- **D** не нужен: Forgejo закрывает задачу без нового сервиса.

<details>
<summary>📋 План перехода на вариант C</summary>

1. **Исходники.** Сделать ElementsUI на Forgejo (`xPOE-Studio/ElementsUI`) главным репозиторием. GitHub - push-зеркало или удалить. Поправить `repository` в `package.json`.
2. **Имя пакета.** Реестр Forgejo не проксирует npmjs, поэтому весь реестр на него переключать нельзя: остальные зависимости перестанут ставиться. Свой пакет выделяется через scope, например `@xpoe/poe-svelte-ui-lib`. Адрес реестра организации - `https://git.xpoe.pro/api/packages/xPOE-Studio/npm/`.
3. **Приложения не меняют импорты.** В DevCloud, DevTerminal и WebApp ESP зависимость пишется алиасом, импорты `poe-svelte-ui-lib` и `poe-svelte-ui-lib/protocols` остаются как есть:

   ```json
   "poe-svelte-ui-lib": "npm:@xpoe/poe-svelte-ui-lib@^X.Y.Z"
   ```

   `.npmrc` в корне каждого приложения:

   ```
   @xpoe:registry=https://git.xpoe.pro/api/packages/xPOE-Studio/npm/
   //git.xpoe.pro/api/packages/xPOE-Studio/npm/:_authToken=${FORGEJO_NPM_TOKEN}
   ```

   Строка с токеном нужна, только если пакет закрытый. Токен - в переменной окружения, не в файле.

4. **CI библиотеки.** Перенести `npm_publish.yaml` в `.forgejo/workflows/`, `runs-on: ubuntu-24`. Публиковать с токеном Forgejo с правом `write:package`, вместо OIDC npmjs. Job обновления DevCloud переносится как есть, клонирует внутри сети.
5. **CI облака.** Если пакет закрытый, `npm ci` в `DevCloud/Dockerfile` нужен токен. Передавать его секретом сборки BuildKit (`RUN --mount=type=secret,id=npmrc,target=/app/.npmrc npm ci`), а не через `COPY .npmrc` и не `ARG`: так токен не попадёт в слои образа в Harbor.
6. **Разработчик.** Для закрытого пакета токен нужен один раз в `~/.npmrc` или переменной окружения: DevTerminal и WebApp ESP собираются локально.
7. **`npm run Sync`** библиотеки кладёт собранную библиотеку в `node_modules/poe-svelte-ui-lib` терминала и облака. С алиасом путь в `node_modules` не меняется, скрипт трогать не нужно.
8. **Документация.** README библиотеки и разделы выпуска в AGENTS всех проектов, этот файл, обзоры `.knowledgebase/Overview.md`.

</details>

## 💡 Полезно знать

- 🔁 Выпуск библиотеки всегда тянет за собой DevTerminal и веб ESP. После веба ESP прошивки всех устройств ESP пересобираются и отправляются в облако. Смена реестра этого не меняет.
- 🔒 Токены не попадают в git, логи и слои образов: только секреты CI, переменные окружения и секреты сборки BuildKit.
- 📌 Версия `npm` в CI закреплена, поднимается вручную. При переходе на Forgejo публикация идёт по токену, требование npm 11.5.1+ для OIDC уходит.
- 🧪 Перед переездом проверить на отдельной версии (`X.Y.Z-rc.1` с тегом `next`), что DevCloud, DevTerminal и WebApp ESP ставят пакет по алиасу и проходят проверку типов.
