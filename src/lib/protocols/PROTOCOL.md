# 📡 Протокол обмена с устройствами

Единый язык, на котором устройства на прошивках ProdFactory-ESP и ProdFactory-STM говорят между собой и с программами вокруг них: DevCloud, DevTerminal и веб-интерфейсом ESP. Здесь описано, как устроен пакет, как он адресуется и как едет по разным проводам.

## ✨ Главное

- 📦 По всем проводам ходят одни и те же записи `[TrgBusID, HAR, Payload]`. Отправитель у пакета один, поэтому его адрес пишется один раз на пакет, а не в каждой записи.
- 🚌 На CAN и CAN FD адрес отправителя и важность пакета лежат в 29-битном ID кадра. Контрольную сумму считает сам CAN, своей в пакете нет.
- 🔗 На RS485, LoRa и UART-консоли пакет несёт адрес отправителя и одну контрольную сумму на весь пакет.
- 🚦 У пакета 4 уровня важности. На CAN важный пакет обгоняет фоновый.
- 🌐 WebSocket не меняется: конверт `{HAR, VAL}`.
- 💬 Текст события устройство шлёт кодом из словаря сообщений `dictionaries/poe_msg.yaml`, облако показывает его на языке пользователя.
- 🔐 Устройство доказывает облаку, что оно то самое, токеном, который получает при первом подключении.

## 🧩 Где живёт код

- 🔧 В прошивках: компоненты `poe_cbor` и `api_service`.
- 💻 В программах: `poe-svelte-ui-lib/protocols` из этой библиотеки.

Байты в обоих местах совпадают, это проверяют тесты: `npm run Test` сверяет байты с эталонами из прошивки. Таблица соответствия функций - в конце документа.

## 📦 Пакет

Пакет - это список записей. Каждая запись говорит: кому, какая команда и какие данные. От кого - знает канал: ID кадра на CAN, заголовок пакета на RS485, UART и LoRa.

<details>
<summary>🔬 Записи пакета</summary>

```
0x9F  [TrgBusID, HAR, Payload]  [ ... ]  0xFF
```

Записи - CBOR-массив неопределённой длины: `0x9F` в начале, `0xFF` в конце. Внутри одна или несколько записей, разным получателям или одному, порядок сохраняется. Конец по `0xFF` позволяет отбросить добивку последнего кадра CAN FD.

Запись - массив ровно из трёх элементов (`0x83`).

| Поле       | Тип                | Что это                          |
| ---------- | ------------------ | -------------------------------- |
| `TrgBusID` | uint16             | Кому. `0xFFFF` значит всем       |
| `HAR`      | uint16             | Заголовок, команда и флаг ответа |
| `Payload`  | одно значение CBOR | Данные команды                   |

Числа в записях пишутся кратчайшим способом: до 23 - 1 байт, до 255 - 2, до 65535 - 3.

</details>

## 🚦 Важность пакета

У пакета один из 4 уровней. Меньше число - важнее пакет. На CAN уровень стоит в старших битах ID, поэтому при одновременной передаче важный кадр выигрывает арбитраж.

| Уровень | Что идёт                                                         | Примеры                                                                                                        |
| ------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 0       | Самое важное: перезагрузка, сброс, обновление, включение привода | `SystemRestart`, `SystemDefaultConfig`, `SystemResetStorage`, `FirmwareUpgrade*`, `MotionEnable`               |
| 1       | Служебные команды, настройки и основная работа                   | `ModuleConfig`, `ModuleInfo`, `ModuleFind`, `MotionTarget`, `MotionVelocity`, `MotionAngle`, `OrientationData` |
| 2       | Вспомогательные потоки и данные                                  | `ModuleStream*`, `ModuleTelemetry*`, `SystemFileSystem`                                                        |
| 3       | Графики, отладка и поток данных интерфейса                       | `DebugPlot`, `DebugLog`, `SystemDataStream`                                                                    |

<details>
<summary>⚙️ Как выбирается уровень</summary>

- Важность команды - четвёртая колонка словаря `poe_cmd.yaml`. У команд устройств (коды до 4096) она обязательна, генератор без неё падает. У команд облака её нет, для них - 2. Генератор кладёт её в `CMD_Priority` (`poe_cmd.h`) и `ARGUMENT_PRIORITIES` (`generated/poe_cmd.ts`), в библиотеке - `dictionary.priority(код)` и `packetPriority(HAR записей)`.
- Пакет из нескольких записей получает самый важный уровень из своих записей.
- Ответ `OK!` и `ER!` на запрос уходит с уровнем запроса: ответ на уставку не застревает за настройками.
- Код прошивки может задать уровень сам при отправке (`priority` у `CAN_Send`), он важнее таблицы.
- На RS485, UART и LoRa уровня в пакете нет: там нет арбитража.

</details>

## 🏷️ Команда (HAR)

Одно 16-битное число несёт сразу три вещи: вид сообщения (`GET`, `SET`, `OK!`, `ER!`), код команды из словаря и флаг «ответь мне».

- 🙋 Устройство отвечает только на запрос с флагом ответа. Сам ответ всегда без флага.
- 📈 Телеметрию и потоки данных шлют без флага, чтобы не ждать подтверждений.
- 🔢 Имена `"GET"` и `"ModuleConfig"` не передаются ни по шине, ни по WebSocket, только коды. Имена нужны людям: интерфейсы, журналы и документация расшифровывают `HAR` по словарю.

<details>
<summary>🔬 Раскладка битов</summary>

```
биты 15-14  заголовок  0 GET, 1 SET, 2 OK!, 3 ER!
биты 13-1   команда    код из словаря, 0..8191
бит 0       ответ      1 - получатель должен ответить
```

В прошивке `HAR` это `har_t` из `poe_cmd.h`, собирается макросами `HAR(h, a)` (с ответом) и `HAR_NR(h, a)` (без). В библиотеке числами это `makeHar` и `splitHar`, словами - `encodeHar(заголовок, аргумент, ответ?, словарь?)` (аргумент - имя или код) и `decodeHar(har, словарь?)`, который возвращает `{ header, argument, code, reply }`. `makeHar`, `encodeHar`, `encodeRecords` и `encodeFrame` бросают `RangeError`, если заголовок, команда, BusID или HAR вне диапазона; `encodeHar` с неизвестным заголовком или именем не из словаря бросает `Error`.

</details>

## 📖 Словарь команд

Коды команд записаны в одном файле: `src/lib/dictionaries/poe_cmd.yaml` этой библиотеки (как добавить команду - в [README словарей](../dictionaries/README.md)). Им пользуются все: прошивки, облако, терминал и веб-интерфейс. Все отладочные команды начинаются с `Debug`: `DebugLog` это 11, `DebugPlot` это 12.

- 🔧 Команды устройств - коды 0-4095.
- ☁️ Команды самого облака DevCloud (чаты, журнал, состояние устройств) - коды 7000-7999.
- 🧱 4096-6999 и 8000-8191 - резерв.

<details>
<summary>⚙️ Копии словаря и словарь устройства</summary>

- `poe_cmd.h` прошивок генерируется из `poe_cmd.yaml` командой `npm run Generate` (`src/lib/dictionaries/firmware/poe_cmd.h`, вручную не править). В прошивках лежат копии словаря `.framework/poe_cmd.yaml` и заголовка, сборка сверяет их между собой.
- Часть аргументов словаря - задел, прошивки их пока не обрабатывают: `SystemBackup`, `ModuleBindKey`, `ModList`, `ModuleMode`, `ModuleTelemetry2-ModuleTelemetry5`, `FirmwareUpgradeError`, `MotionVelocity`, `MotionAngle`, `OrientationOffset`, `OrientationAccelCalibrate`, `OrientationMagCalibrate`, `OrientationGyroscopeCalibrate`. Коды у них закреплены и не меняются. Такой аргумент модуль примет, но ответа не будет, поэтому в примерах берут реальные команды (`ModuleConfig`, `ModuleInfo`, `SystemFileSystem`).
- Словарь один на стек: прошивки собираются с его копией, поэтому приложения берут встроенный `DEFAULT_DICTIONARY`. Объект словаря (`createDictionary(codes)`): `code(имя)`, `name(код)`, `header(код)`, `har(заголовок, команда, ответ)`.
- Команду, которой нет в словаре, задают числом: `code` и `har` принимают код строкой, десятичный или HEX (`"4097"`, `"0x1001"`), а `name` для неизвестного кода возвращает его же числом строкой, так что запись «туда и обратно» сходится.
- Такой словарь принимают `encodeHar`, `decodeHar`, `encodeWsEnvelope`, `decodeWsEnvelope`, `encodeXPoeDebugFrame` (последний аргумент), `createXPoeDebugParser({ dictionary })` и связь `GUIRenderer` (поле `dictionary`). Без него берётся встроенный.

</details>

## 💬 Сообщения устройств

Текст события в ответе или пуше устройство шлёт не строкой, а кодом. Все коды записаны в одном файле: `src/lib/dictionaries/poe_msg.yaml` этой библиотеки, рядом со словарём команд `poe_cmd.yaml`. Коды разбиты на группы, у каждой свой диапазон и приставка имени. У каждого кода уровень (`info`, `warn`, `error`) и текст на русском, английском и китайском. Облако и веб-интерфейс показывают сообщение на языке пользователя.

- 0 или нет поля `Message` - сообщения нет.
- Тексты короткие и понятные пользователю: причина без технических подробностей (подробности прошивка пишет в свой журнал). Изменяемую часть (SSID, номер канала, список полей) устройство шлёт отдельно, массивом `Args`, только если без неё теряется смысл. В шаблоне это `{0}`, `{1}` и дальше по порядку.
- 📚 Новое сообщение сначала добавляют в `poe_msg.yaml`, потом копируют в прошивки (`.framework/poe_msg.yaml` и `poe_msg.h` обоих фреймворков).
- 🗂️ Новое сообщение - в свою группу: код из её диапазона, имя с её приставкой. Новая группа ядра получает диапазон из резерва 900-999.
- 🧯 Те же коды прошивки возвращают при ошибках и пишут в свой журнал, текст на языке пользователя показывает отладочная консоль.

| Группа             | Коды      | Название   | Что                                                        |
| ------------------ | --------- | ---------- | ---------------------------------------------------------- |
| `SYS`              | 1-99      | Система    | Перезагрузка, неизвестная команда, неверный запрос, память |
| `CFG`              | 100-199   | Настройки  | Приём настроек (`config_service`)                          |
| `SystemFileSystem` | 200-299   | Файлы      | Файловая система, загрузка и выгрузка файлов               |
| `FW`               | 300-399   | Обновление | Загрузка и обновление прошивки, обновление модуля по шине  |
| `WIFI`             | 400-499   | Wi-Fi      | Поиск сетей и подключение                                  |
| `API`              | 500-599   | Обмен      | Пакеты, буферы, модули и маршруты                          |
| `BUS`              | 600-699   | Шины       | UART, CAN, SPI, I2C, GPIO, прерывания                      |
| `NET`              | 700-799   | Сеть       | Веб-сервер, HTTP, WebSocket, SSDP                          |
| `LORA`             | 800-899   | LoRa       | Радио LoRa                                                 |
| -                  | 900-999   | -          | Резерв для новых групп ядра                                |
| `DEV`              | 1000-1999 | Изделия    | Сообщения изделий каталога (`catalog/<CatalogID>`)         |
| `DRV`              | 2000-2999 | Драйверы   | Драйверы датчиков и микросхем, утилиты                     |
| -                  | 3000+     | -          | Резерв                                                     |

<details>
<summary>🧯 Коды ошибок и журнал прошивок</summary>

- Функции обоих фреймворков возвращают `poe_err_t`: `POE_OK` (0) - успех, иначе код причины из этого словаря.
- Событие в журнале - тоже код: `LOG_E("RM3100", MSG_DRV_BIST_FAILED, "0x%02X\t0x%02X", bist, axes)` уходит в консоль пакетом `DebugLog` с текстом `MSG 2022 0x30\t0x40`, xPOE-Debug показывает его на языке пользователя.
- Текстов событий в прошивках нет, новое событие сначала добавляют в `poe_msg.yaml`.

</details>

<details>
<summary>⚙️ Формат и функции</summary>

```
WebSocket, ответ или пуш   {HAR, VAL: {DevSN, ModSN, Message: 404, Args: ["Home 5G"], Payload}}
шина, ER! модуля           [TrgBusID, HAR (ER!), {Message: 404, Args: ["Home 5G"]}]
консоль, DebugLog          [уровень, "HAR 0xC048", "MSG 404 Home 5G", FHS]
```

- 🚌 Шина: у ответа `ER!` модуль кладёт в `Payload` CBOR-карту `{Message: код, Args?: [строки]}`. У `OK!` пакет шины не меняется - в `Payload` голые данные.
- 🔁 Хаб ESP, пересылая `ER!` модуля клиенту (`RouteResponseToClient`), берёт `Message` и `Args` из `Payload` модуля и кладёт их в конверт `{HAR, VAL: {DevSN, ModSN, Message, Args?, Payload}}`.
- 🖥️ Консоль: сообщение приходит отдельным пакетом `DebugLog` с тегом `HAR 0x....` (HAR ответа) и текстом `MSG <код>[ <арг1>[<TAB><арг2>...]]`: пробел после кода, TAB между параметрами (в SSID бывают пробелы). Таблица консоли оставляет текст в колонке «Значение» как пришёл (`MSG 404 Home 5G`), а сообщение на языке (`Не удалось подключиться к Wi-Fi Home 5G, восстановлена прежняя сеть`) показывает в колонке «Команда» под командой. Строка `xPoeDebugRow` несёт его в полях `message` и `level`, их собирает `xPoeDebugMessage(payload, lang)` - и для `DebugLog`, и для карты `{Message, Args}` в `Payload` ответа `ER!`. Разбор текста - `parseDebugLogMessage(text)` -> `{ Message, Args? }` или `null`.

- `Message` - число 0..65535, `Args` - массив строк и чисел, только если у сообщения есть параметры. Тип в библиотеке - `DeviceMessage = { Message: number, Args?: (string | number)[] }`.
- `poe_msg.yaml`: раздел `groups` (`ИМЯ: { range: [от, до], ru, en, zh }`) и раздел `messages` (строки `- { code, group, name, level, ru, en, zh }`). `name` - имя для C в стиле `UPPER_SNAKE` с приставкой группы (`FS_FILE_NOT_FOUND`), в прошивке это `MSG_<name>` из `poe_msg.h`. Префиксов `ER:`/`WR:` в тексте нет, вид сообщения задаёт `level`.
- `npm run Generate` (и `prepack`) из `poe_msg.yaml` генерирует `dictionaries/generated/poe_msg.ts` (`MESSAGE_GROUPS`: группа -> диапазон и название на языках, `DEVICE_MESSAGES`: код -> запись с группой, `MESSAGE_CODES`: имя -> код) и `dictionaries/firmware/poe_msg.h` (`typedef enum { MSG_NONE = 0, MSG_SYS_RESTARTING = 1, ... } api_msg_t`, раздел-комментарий на каждую группу). Генератор падает на пересечении диапазонов групп, коде вне диапазона своей группы, имени без приставки группы, повторе кода или имени, неизвестном `level`, пустом тексте и разных параметрах в языках. Оба файла не правятся руками, `poe_msg.yaml` и оба заголовка прошивок есть в пакете (`poe-svelte-ui-lib/dictionaries/poe_msg.yaml`, `poe-svelte-ui-lib/dictionaries/firmware/poe_cmd.h`, `poe-svelte-ui-lib/dictionaries/firmware/poe_msg.h`).
- `formatDeviceMessage(code, args?, lang?)` возвращает `{ text, level, group, groupName }` (тип `FormattedDeviceMessage`) или `null` (0, нет кода, не число). `group` - код группы (`"FS"`), `groupName` - её название на языке (`"Файлы"`). Без `lang` - язык по умолчанию, приложение передаёт текущий язык (`getLanguage()`). Нет перевода на язык - английский текст. Неизвестный код - `"#1234"` (с параметрами `"#1234: a, b"`) и уровень `info`, группа - по диапазону кода, код из резерва - `group` и `groupName` равны `null`. Параметра не хватило - на его месте `?`.
- Параметры `{0}`, `{1}`... у сообщения есть, только если без них теряется смысл: поля настроек, SSID, номер канала, адрес или значение регистра. Что значит каждый параметр, видно из текста шаблона.

```ts
import { formatDeviceMessage } from "poe-svelte-ui-lib/protocols"
import { getLanguage } from "poe-svelte-ui-lib/locales"

const shown = formatDeviceMessage(VAL.Message, VAL.Args, getLanguage())
/* { text: "Не удалось подключиться к Wi-Fi Home 5G, восстановлена прежняя сеть", level: "warn", group: "WIFI", groupName: "Wi-Fi" } */
```

</details>

<details>
<summary>🔀 Переход</summary>

На один выпуск облака `Message` ещё может прийти строкой от старой прошивки (`"OK: ModList Changed"`). `formatDeviceMessage` такую строку не разбирает и возвращает `null`, облако показывает строку как есть. Блок удаляется со следующим выпуском.

</details>

## 📄 Данные (Payload)

`Payload` это всегда ровно одно значение CBOR: объект, массив, число, строка, набор байт или «ничего». Поля «формат данных» нет, тип видно по самому CBOR.

<details>
<summary>📦 Как кодируются данные</summary>

| Данные                        | Как кодируются                                                         |
| ----------------------------- | ---------------------------------------------------------------------- |
| Объект, массив, число, строка | Как есть, например `{CfgGroup: "CFG"}`                                 |
| Набор сырых двоичных полей    | Байтовая строка `h'...'`. В прошивке `CBOR_PACK`, разбор `CBOR_UNPACK` |
| Ничего                        | `null` (`0xF6`). В прошивке это `data_len = 0`                         |
| Ответ `ER!` модуля на шине    | Карта `{Message: код, Args?: [строки]}` (раздел «Сообщения устройств») |

</details>

## 🔄 Обновление модуля по шине

Загрузчик модуля STM сам читает новую прошивку у сервера, как файл. Сервер - тот, кто начал обновление: хаб ESP (прошивку он скачал из каталога облака) или терминал (файл с диска). Сервер только отвечает на запросы и ничего не помнит о ходе, поэтому повторы, порядок и проверку ведёт загрузчик.

```
сервер → модуль      SET FirmwareUpgradeStart   размер и CRC32 образа        (повтор раз в секунду, пока нет ответа)
загрузчик → сервер   OK! FirmwareUpgradeStart   место стёрто
загрузчик → сервер   GET FirmwareUpgradeRead    смещение, сколько байт       (по порядку, до конца образа)
сервер → загрузчик   OK! FirmwareUpgradeRead    смещение, данные
загрузчик → сервер   OK! FirmwareUpgradeDone    CRC32 сошлась, приложение запускается
```

<details>
<summary>⚙️ Команды и ответы</summary>

Поля сырые: `Payload` - байтовая строка, поля подряд, little-endian.

| Команда                    | Кто кому           | Поля                                        | Ответ                                                                                                                              |
| -------------------------- | ------------------ | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `SET FirmwareUpgradeStart` | сервер → модуль    | размер `u32`, CRC32 образа `u32`            | `OK!` без данных - место стёрто, загрузчик начинает читать; `ER!` `{Message: 3}` неверный размер, `{Message: 5}` Flash не стёрлась |
| `GET FirmwareUpgradeRead`  | загрузчик → сервер | смещение `u32`, сколько байт `u8`           | `OK!` - то же смещение `u32` и данные с него; `ER!` `{Message: 320}` - у сервера нет файла для модуля                              |
| `FirmwareUpgradeDone`      | загрузчик → сервер | `OK!` без данных или `ER!` `{Message: код}` | ответа нет                                                                                                                         |

- **Старт.** Приложение модуля на `FirmwareUpgradeStart` перезагружается в загрузчик и не отвечает. Сервер повторяет команду раз в секунду, пока загрузчик не ответит `OK!` или не начнёт читать. Загрузчик ждёт команду 5 секунд после сброса. Тот же старт от того же сервера посреди сеанса загрузчик не начинает заново, а снова отвечает `OK!`.
- **Сервер** - отправитель `FirmwareUpgradeStart` (`SrcBusID`). Чтение уходит ему, ответ на чтение принимается только от него.
- **Кусок** выбирает загрузчик: 40 байт на CAN FD (ответ в одном кадре), 224 на LoRa, 240 по консоли. Смещение в ответе нужно, чтобы запоздалый ответ на прошлое чтение не записался не туда. Ответ короче запрошенного бывает только в конце образа.
- **Окно.** По CAN FD загрузчик не ждёт ответа на каждый кусок, а держит в пути до 8 чтений подряд. Сервер отвечает на каждое чтение отдельно, по порядку. Загрузчик принимает только следующий по порядку кусок, а на каждый принятый сразу просит ещё один. По консоли и LoRa чтение одно.
- **Важность.** Пакеты обновления (`FirmwareUpgradeStart`, `Read`, `Done`) идут с важностью 0. Пока идёт обновление, оно главное на шине, поэтому обновляют остановленное изделие.
- **Повторы.** Нет ответа на первое чтение окна - загрузчик читает окно заново с этого места: на CAN и консоли через 300 мс, на LoRa через 1.5 с, до 5 раз подряд. Не вышло - сеанс бросается, загрузчик сообщает `ER! FirmwareUpgradeDone {Message: 302}` и ждёт новый старт: начало области приложения уже стёрто, запускать нечего.
- **Конец.** Прочитано столько байт, сколько в старте, - загрузчик сверяет CRC32 образа. Сошлась - пишет начало образа (адрес стека и точку входа) последним, сообщает `OK! FirmwareUpgradeDone` и запускает приложение. Не сошлась - `ER! FirmwareUpgradeDone {Message: 306}`, приложение не запускается.
- **Ход** сервер считает сам по смещению чтений.
- **Несколько модулей.** Сеанс загрузчика - один и только со своим сервером, а сервер может раздавать файлы нескольким модулям сразу: каждому по его `SrcBusID`.

```
шина, чтение   [TrgBusID сервера, HAR (GET FirmwareUpgradeRead), h'00a00000 28']    смещение 40960, 40 байт
шина, ответ    [TrgBusID модуля, HAR (OK! FirmwareUpgradeRead), h'00a00000 ...']   то же смещение и 40 байт
```

Код загрузчиков - ProdFactory-STM (`catalog/00.00.491-01` CAN FD, `catalog/25.00.000-01` LoRa), сервер - `upgrade_service` ProdFactory-ESP и `updateModuleFirmware` библиотеки.

</details>

## ✅ Контрольная сумма (CRC)

На CAN каждый кадр защищает сам контроллер, своей контрольной суммы в пакете нет. Рамка RS485, UART-консоли и LoRa несёт одну CRC-16 на весь пакет: она защищает и отправителя, и все записи. Рамка с неправильной CRC отбрасывается целиком.

<details>
<summary>🔬 Алгоритм</summary>

- CRC-16/KERMIT: полином `0x8408` (отражённый `0x1021`), начальное значение 0, `check("123456789") = 0x2189`.
- Считается по байтам пакета от `0x83` до `0xFF` записей включительно, поле CRC не входит.

</details>

## 📍 Адреса

- 🆔 Адрес модуля на шине (BusID) - это CRC-16 его серийного номера.
- 📢 Адрес `0xFFFF` значит «всем».
- 🖥️ Адрес `0x0000` - внешний клиент: терминал или отладка облака.
- 🔁 Хаб и консоль ядра пересылают запросы клиентов модулям от своего имени.

<details>
<summary>🔬 Правила адресации</summary>

- BusID модуля это CRC-16 его серийного номера. Значения `0x0000` и `0xFFFF` модулю не выдаются.
- На шине модуль принимает записи со своим BusID и с `0xFFFF`. Свои же пакеты, вернувшиеся эхом (CAN и RS485), он узнаёт по `SrcBusID` и пропускает.
- `0x0000` как отправитель бывает только у внешнего клиента: в консоли и у DevTerminal, подключённого к шине адаптером. На одной шине CAN - не больше одного такого клиента.
- В консоли адрес `0xFFFF` значит «этот модуль». `0x0000` и свой BusID прошивки понимают так же и передают запрос дальше как адресный, поэтому на неизвестную команду придёт `ER!`.
- Если обработчика команды нет, `OK!`, `ER!` и широковещательные записи отбрасываются молча. `GET` и `SET`, адресованные модулю, отбрасываются с записью в лог.

</details>

<details>
<summary>🔁 Пересылка через хаб и консоль ядра</summary>

Клиент (консоль, веб, облако) просит модуль за хабом. Хаб кладёт запрос на шину от своего имени: на CAN в ID кадра его BusID, на RS485 и LoRa - в заголовке пакета. Модуль отвечает хабу, хаб отдаёт ответ клиентам.

- Хаб находит модуль по `ModSN` из запроса клиента в своём `CFG.ModList` и шлёт ему запись с `TrgBusID` модуля по шине, на которой модуль найден.
- Хаб запоминает, по какому каналу клиента (консоль, локальный веб, облако) пришёл последний запрос к этому модулю. Ответ `OK!` или `ER!` модуля, адресованный хабу, уходит в этот канал, завёрнутый в конверт с `ModSN` модуля.
- Рассылки модулей без запроса (`SET` на `0xFFFF` с флагом ответа) хаб подтверждает `OK!` и отдаёт клиентам как данные `OK!`.
- Отправитель на шине - всегда сам хаб, поэтому кадры двух хабов на одной шине CAN не совпадают по ID, а ответ модуля получает только тот хаб, который спрашивал.

</details>

## 🔌 Как пакет едет по разным проводам

- 🚌 **CAN и CAN FD** - записи режутся на кадры по 8 или 64 байта, отправитель, важность и номер кадра - в 29-битном ID.
- 🔗 **RS485 и UART-консоль** - пакет `[SrcBusID, записи, CRC16]` в сплошном потоке.
- 📻 **LoRa** - тот же пакет `[SrcBusID, записи, CRC16]` целиком в одном радиокадре.

<details>
<summary>🚌 CAN и CAN FD: ID кадра</summary>

Только расширенный 29-битный ID (CAN 2.0B). Кадры со стандартным 11-битным ID пропускаются.

```
биты 28-27  важность      0..3, 0 - самый важный
биты 26-11  SrcBusID      адрес отправителя
бит  10     последний     1 - последний кадр пакета (или единственный)
биты 9-3    номер кадра   0, 1, 2 ... по кругу через 127
биты 2-0    счётчик       номер пакета у отправителя, по кругу 0..7
```

- В данных кадров - записи пакета подряд (`0x9F ... 0xFF`), без служебных байтов. Классический CAN - по 8 байт, CAN FD - по 64, последний кадр FD добивается до ближайшей длины DLC.
- Пакет собирается по паре «отправитель + счётчик». Номера кадров должны идти подряд: пропуск - пакет выбрасывается с предупреждением в лог. Так ловится кадр, который отправитель отдал на шину, а этот приёмник не успел принять (кадр подтверждает любой узел).
- Кадр с номером 0 начинает сборку заново, даже если старая с тем же ключом не закончена. Исключение - переход номера через 127 в длинном пакете.
- Недособранный пакет выбрасывается через 250 мс.
- Целостность каждого кадра проверяет контроллер CAN (CRC-15 у классического, CRC-17 и CRC-21 у FD).
- Отправитель в ID уникален, поэтому два узла никогда не передают кадры с одинаковым ID. Свои кадры, вернувшиеся эхом, узел узнаёт по `SrcBusID` в ID.
- При равной важности арбитраж выигрывает меньший `SrcBusID`. Промежуточные кадры (бит 10 = 0) обгоняют последние кадры той же важности и того же отправителя.
- Длина пакета: 128 кадров без перехода номера через 0 - 1 КБ на классическом CAN и 8 КБ на FD. Длиннее можно: номер идёт по кругу, проверка «подряд» работает так же.

Пример: ядро `0xABCD` спрашивает `GET ModuleConfig {}` у привода `0x1234`, важность 2, счётчик 5, CAN FD.

```
ID   0x155E6C05   важность 2, Src 0xABCD, последний, кадр 0, счётчик 5
DATA 9F 83 19 12 34 18 49 A0 FF   (9 байт, DLC 12, добивка 3 байта)
```

</details>

<details>
<summary>🔗 RS485, UART-консоль и LoRa: пакет с CRC</summary>

```
0x83  0x19 Src_hi Src_lo  0x9F [записи] 0xFF  0x19 CRC_hi CRC_lo
```

- Рамка - CBOR-массив из трёх элементов: `SrcBusID`, записи, `CRC16`.
- `SrcBusID` и `CRC16` всегда пишутся тремя байтами `0x19 hi lo`, даже если число маленькое. Поэтому начало пакета всегда `0x83 0x19 ?? ?? 0x9F` - это примета начала пакета в потоке.
- CRC-16/KERMIT (полином `0x8408`, начальное значение 0, `check("123456789") = 0x2189`) считается от `0x83` до `0xFF` записей включительно.
- Рамка с неверной CRC выбрасывается целиком, поиск начала продолжается со следующего байта.
- RS485: пауза сбрасывает недособранный пакет, в прошивке 20 мс, на компьютере 100 мс.
- UART-консоль: пакеты идут вперемешку с текстом загрузчика, всё, что не пакет, - текст. Недособранный пакет сбрасывается после 100 мс тишины.
- LoRa: пакет целиком в одном радиокадре. Своя CRC нужна и здесь: CRC радио можно выключить в настройках `LORA.Cfg`.
- Ложное начало (байты, похожие на заголовок, перед настоящим пакетом) не держит поток: если дальше в буфере уже есть целый пакет с верной CRC, поиск переходит к ней.

</details>

## 🐞 Отладка в консоли

Прошивка присылает в консоль отладочные сообщения и значения для графиков. Это обычные пакеты, адресованные внешнему клиенту, без флага ответа.

<details>
<summary>📦 Отладочные пакеты</summary>

Прошивка шлёт отладочные пакеты со своим BusID в `SrcBusID`, записями с `TrgBusID = 0` и без флага ответа.

| Команда           | Payload                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `OK! DebugLog`    | `[уровень, тег, текст или байты, FHS]`. FHS это свободная память устройства                       |
| `OK! DebugPlot`   | `{Группа.Имя: float32, ...}`, один вызов `LOG_PLOT`                                               |
| `OK! DebugMirror` | `{Dir, If, Trg, Src, HAR, ModSN, Val}`: копия пакета другого интерфейса, только на уровне `TRACE` |

Рассылки устройства без запроса (`OK! ModuleConfig` при изменениях, `SystemDataUpdate`, `SystemDataStream`, сообщения) идут в консоль так же, как в веб и облако, при любом уровне логов, кроме `OFF`.

На уровне `TRACE` консоль получает копию каждого пакета других интерфейсов в обёртке `OK! DebugMirror`: `Dir` - `rx` (принят) или `tx` (отправлен), `If` - биты интерфейсов (`iface_t` фреймворка), `Trg`, `Src` - адреса, `HAR` - число HAR пакета, `ModSN` - серийный номер (если есть), `Val` - данные пакета как есть (конверт `{HAR, VAL}` WebSocket или Payload шины). Пакеты самой консоли не копируются. GUI устройства обёртку не разбирает, его значения приходят обычными рассылками.

На запрос из консоли прошивка отвечает голым `Payload`. Если у ответа есть сообщение `Message`, оно приходит отдельным пакетом `DebugLog`: тег `HAR 0x....`, текст `MSG <код>[ <арг1>[<TAB><арг2>...]]` (раздел «Сообщения устройств»). Таблица консоли показывает его текстом на языке пользователя в колонке «Команда», «Значение» остаётся как пришло.

</details>

<details>
<summary>👀 Колонка VALUE в консоли</summary>

Таблица консоли показывает `Payload` наглядно, в стиле YAML (`formatXPoeDebugValue`), а окно строки - развёрнуто (`formatXPoeDebugPretty`). Строку VALUE можно скопировать и вставить в поле Value: уйдёт тот же CBOR.

| Payload                     | Строка VALUE                                          |
| --------------------------- | ----------------------------------------------------- |
| карта                       | `CFG.DevName: ESP32-Pico-1, CFG.WiFiMode: 1` без `{}` |
| вложенная карта, массив     | `Net: {SSID: "Home 5G", Ch: 6}, List: [1, 2]`         |
| пустая карта, пустой массив | `{}`, `[]`                                            |
| байтовая строка             | `h'0C73'`                                             |
| число, логическое, null     | `42`, `12.3`, `true`, `null`                          |
| строка                      | всегда в кавычках: `"Home 5G"`, `"123"`               |
| не CBOR                     | HEX байт: `AB CD`                                     |
| `DebugLog`                  | `🟡 · тег · текст`                                    |

- Строка-значение всегда в кавычках `"..."` (внутри `\"` и `\`): строку не спутать с числом, IP или `true`. Ключ-строка пишется без кавычек, кавычки у ключа - если он похож на число, `true`, `false` или `null`, пустой, содержит `:`, `,`, `[]{}`, `#`, перевод строки, пробелы по краям или начинается с кавычки или `h'`.
- Порядок пар и типы ключей - как на проводе: ключ-число без кавычек (`1: x`), ключ-строка из цифр в кавычках (`"1": x`).
- Окно строки показывает тот же `Payload` блочным YAML с отступом 2 пробела.

<details>
<summary>Подробнее о числах и окне</summary>

- float32 с провода декодер отдаёт кратчайшей записью того же float32: `12.3`, а не `12.300000190734863`, `0.005`, а не `0.004999999888241291`. Так числа чистые везде - в журнале, полях GUI и графиках. Обратно такое число уходит float64, прошивки читают любое число CBOR (`CBOR_DecodeNumber`). Целые за пределами 2^53 показываются точно (`18446744073709551615`).
- `.inf`, `-.inf`, `.nan` - бесконечности и NaN.
- Корень не карта - как одно значение: `[1, 2]`, `h'01FF'`, `42`, `"123"`.
- Окно: вложенная карта или массив - с новой строки с отступом 2, элементы массива через `- `.

```yaml
Mode: 1
Net:
  SSID: Home 5G
  Ch:
    - 1
    - 6
Raw: h'01'
```

</details>

</details>

<details>
<summary>✍️ Поле Value в консоли</summary>

Значение команды из консоли (DevCloud, DevTerminal) превращает в `Payload` функция `xPoeDebugValueFromText(text)`. Поле понимает тот же поток YAML, что колонка VALUE.

| Ввод                          | Что уходит                                      |
| ----------------------------- | ----------------------------------------------- |
| пусто                         | пустой `Payload`                                |
| `CfgGroup: CFG, CFG.SCLL: 3`  | карта (скобки у корневой карты можно не писать) |
| `{CfgGroup: "CFG"}`           | карта в скобках                                 |
| `[1, 2]`, `12`, `"12"`, `abc` | массив, число 12, строка `12`, строка `abc`     |
| `h'0A 1B'`                    | байтовая строка CBOR (пробелы внутри можно)     |
| `0x0A1B`                      | эти байты как есть, это уже готовый CBOR        |

- Голые цифры вроде `10` - это число, а не байт `0x10`.
- Ошибка разбора называет причину и позицию: `ожидалась «,» или «]» (позиция 6)`.

<details>
<summary>Подробнее о разборе</summary>

- Поддерживается поток YAML: карты `{a: 1}`, массивы `[1, 2]`, строки в `"..."` (экранирование через `\`) и `'...'` (кавычка удваивается), `null`/`~`, `true`/`false`, `.inf`/`.nan`, `ключ:` без значения - `null`.
- Ключ без кавычек читается по виду: `1: x` - ключ-число, `"1": x` - ключ-строка.
- Целое за пределами 2^53 уходит точно (uint64), дробное - кратчайшим float16/float32/float64 без потери значения.
- Нечётное число HEX-цифр в `h'..'` или `0x..` - ошибка.

</details>

</details>

## 🌐 WebSocket

Облако, браузер и локальный веб-интерфейс ESP говорят через WebSocket. Сообщение здесь - конверт из двух полей: `HAR` (то же число, что на шине) и `VAL` (данные). Так устроены все соединения: браузер - облако, облако - устройство, веб-интерфейс - устройство.

- 🔢 Команда всегда числом `HAR`: заголовок, код из словаря и флаг ответа. Имён в конверте нет.
- 🆔 В запросе к устройству указан серийный номер устройства.
- 🧩 Можно обратиться к конкретному модулю на шине, устройство-хаб перешлёт запрос с тем же `HAR` без перевода. Так модуль получает и команды, которых хаб не знает.
- 🙋 Флаг ответа работает как на шине: запрос с флагом ждёт ответа, ответ и телеметрия идут без флага.
- 📝 Событие из ответа (код сообщения) облако сохраняет в журнал устройства.

<details>
<summary>📦 Конверт</summary>

```
запрос  {HAR, VAL: {DevSN, ModSN?, TrgBusID?, SrcBusID?, Payload?}}
ответ   {HAR, VAL: {DevSN, ModSN, Message, Args?, Payload}}
```

| Поле  | Тип    | Что это                                                                                            |
| ----- | ------ | -------------------------------------------------------------------------------------------------- |
| `HAR` | uint16 | Заголовок (биты 15-14), код аргумента (биты 13-1), флаг ответа (бит 0)                             |
| `VAL` | объект | Данные: адрес (`DevSN`, `ModSN`), `Payload`, у ответа `Message` (код) и `Args`, у облака свои поля |

| Заголовок | Код (биты 15-14) | Флаг ответа по умолчанию |
| --------- | ---------------- | ------------------------ |
| `GET`     | 0                | есть                     |
| `SET`     | 1                | есть                     |
| `OK!`     | 2                | нет                      |
| `ER!`     | 3                | нет                      |

- `DevSN` обязателен в запросе к устройству и должен совпасть с его серийным номером.
- `ModSN` - модуль, которому адресован запрос. Без него запрос идёт самому устройству.
- `Message` в ответе - код события из `poe_msg.yaml`, `Args` - его параметры (раздел «Сообщения устройств»). DevCloud сохраняет сообщение с кодом не 0 в журнал устройства.
- Флаг ответа (бит 0): устройство отвечает только на запрос с флагом. Ответ, пуш и телеметрия - без флага.
- Сообщение без целого `HAR` 0..65535 или с `VAL` не объектом - не конверт, его отбрасывают.
- Код, которого нет в словаре получателя, не ошибка: имя для журнала - строка из числа (`"4097"`), сам код сохраняется.

В прошивке запрос принимает `API_Service_ReceiveWsPacket`, ответ собирает `API_Service_BeginResponse`. Ответ модуля с шины устройство-хаб заворачивает в конверт с тем же `HAR`. У `ER!` модуля хаб переносит `Message` и `Args` из `Payload` модуля в `VAL`.

</details>

<details>
<summary>🔁 Пример туда и обратно: GET ModuleConfig модулю за хабом</summary>

`ModuleConfig` = 36. Запрос с флагом ответа: `HAR = (0 << 14) | (36 << 1) | 1 = 0x0049` (73). Ответ `OK!` без флага: `HAR = (2 << 14) | (36 << 1) = 0x8048` (32840).

```
туда     {HAR: 73, VAL: {DevSN: "HUB-SN", ModSN: "MOD-SN", Payload: {}}}
на шине  [TrgBusID модуля, HAR 0x0049, {}], отправитель - хаб (в ID кадра CAN)
обратно  {HAR: 32840, VAL: {DevSN: "HUB-SN", ModSN: "MOD-SN", Message: 0, Payload: {...}}}
```

То же в коде:

```ts
import { encodeWsEnvelope, decodeWsEnvelope, valueToCbor, cborToValue } from "poe-svelte-ui-lib/protocols"

socket.send(valueToCbor(encodeWsEnvelope("GET", "ModuleConfig", { DevSN, ModSN, Payload: {} })))
/* { header: "OK!", argument: "ModuleConfig", code: 36, reply: false, VAL: {...} } или null */
const message = decodeWsEnvelope(cborToValue(new Uint8Array(event.data)))
```

</details>

<details>
<summary>🧰 Функции конверта</summary>

| Функция                                                                           | Что делает                                                                                                                                                        |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `encodeWsEnvelope(header, argument, VAL, reply?, dictionary?)`                    | Собирает `{HAR, VAL}`. `argument` - имя или код. `reply` по умолчанию: `GET`/`SET` - да, `OK!`/`ER!` - нет. Имя не из словаря или значение вне диапазона - ошибка |
| `decodeWsEnvelope(packet, dictionary?)`                                           | Разбирает `{HAR, VAL}` в `{ header, argument, code, reply, VAL }`, не конверт - `null`. Неизвестный код - `argument` строкой из числа                             |
| `encodeHar(header, argument, reply?, dictionary?)`, `decodeHar(har, dictionary?)` | То же для одного числа `HAR`, общие для шины, xPOE-Debug и WebSocket                                                                                              |

Связь `GUIRenderer` (`DeviceLink`) и `createFsTransfer` отдают приложению уже готовый `HAR`: `send(har, payload)`, а ответ ждут по коду аргумента: `waitFor(code, match, timeoutMs)`. Имена `Header`/`Argument` в `eventHandler` компонента - справка автора GUI, в провод они уходят числом.

</details>

<details>
<summary>🔐 Аутентификация устройства в облаке (TOFU)</summary>

Устройство подключается к облаку `wss://{SrvDomain}/ws?DevSN&DevName&DevFW` и публикует потоки в `wss://{SrvDomain}/ws-stream?DevSN&Key&role=publisher`. Доверие устанавливается при первом подключении: облако выдаёт устройству токен, дальше устройство предъявляет его при каждом подключении.

- Токен: 64 hex-символа (32 случайных байта). Облако хранит только его SHA-256 и признак «подтверждён».
- Устройство передаёт токен заголовком `Authorization: Bearer <токен>` в обоих подключениях. В query токен не кладётся.
- Выдача: если у устройства нет подтверждённого токена, облако принимает подключение и присылает новый токен в `SET CloudJoinDevice`, `Payload: {DevToken: "<токен>"}`. Устройство принимает `DevToken` только из облачного WebSocket, сохраняет его и переподключается.
- Подтверждение: первое подключение с верным токеном помечает его подтверждённым. После этого подключение без токена или с неверным токеном облако закрывает кодом `1008`.
- Прошивка без поддержки токена игнорирует `DevToken` и подключается без него. Облако её принимает, пока токен не подтверждён.
- Токен хранится в разделе NVS `config` отдельным ключом `DevToken`, вне групп `ModuleConfig`: его не отдаёт `GET ModuleConfig`, не меняют `SET ModuleConfig` и `SystemDefaultConfig`. При стирании раздела (`SystemResetStorage`, полный сброс настроек, восстановление после повреждения) токен сохраняется в памяти и записывается обратно.
- Если токен потерян (полное стирание флеша) или выдан чужому, администратор сбрасывает его в DevCloud; при следующем подключении устройство получит новый.
- Модули на шине (STM32) к облаку не подключаются, их представляет устройство-хаб.

</details>

## 💡 Полезно знать

- 🧭 `0x83 0x19 ?? ?? 0x9F` - примета начала пакета в потоке RS485 и UART.
- 🚦 На CAN у пакета 4 уровня важности, ответ идёт с уровнем запроса.
- 🔇 На телеметрию устройство не отвечает: у неё нет флага ответа.
- 📚 Новую команду сначала добавляют в `dictionaries/poe_cmd.yaml` библиотеки, новое сообщение - в `dictionaries/poe_msg.yaml`, потом копируют в прошивки.
- 🛰️ Модули на шине к облаку сами не подключаются, их представляет устройство-хаб.
